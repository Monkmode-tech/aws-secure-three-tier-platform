## In plain terms (2-minute read)

**The problem.** Many company websites run on cloud setups that *work* but are
risky: servers anyone on the internet can reach, passwords stored in plain text,
no protection from common attacks, and a single failure that takes the whole
site down.

**What I built.** A blueprint, written as code, that builds a complete, secure
website environment on Amazon Web Services in about 20 minutes and removes it
just as cleanly. I started from a class project that worked but had those exact
risks, found **14 specific weaknesses**, fixed every one, and wrote automated
checks that prove the fixes on the live system.

**Why it matters to a business**

| Business need | How this project delivers it |
|---------------|------------------------------|
| Stay online | Runs across three separate AWS data centers. If one fails, the site keeps serving, and the database switches to a live standby copy automatically. |
| Handle busy periods | Adds servers on its own when traffic rises and removes them when it drops, so you only pay for what you use. |
| Protect customer data | Everything is encrypted. The database cannot be reached from the internet at all. Its password is generated by AWS and kept in a vault; no person ever sees it. |
| Block attacks | A web application firewall filters known attack patterns, malicious sources and request floods before they reach the site. |
| Know when something breaks | Alerts on errors, slowness and failures are emailed automatically, with a live dashboard. |
| Control cost | A $50/month budget alarm, and a full test session costs under $1 because the environment is built on demand and torn down after. |
| Change safely | Every change is reviewed and automatically security-scanned before it can be applied, and the cloud environment is rebuilt identically from code every time. |

**What this shows about how I work.** I can take a system that "works," review it
the way a security team would, explain the risks in business terms, fix them
properly, and prove the result with evidence instead of claims. That is the day
job of a cloud or security engineer.

## Technical summary

A production-style AWS web platform built entirely with Terraform modules:
**WordPress on ECS Fargate in private subnets, behind an ALB with AWS WAF and
TLS, backed by a Multi-AZ, KMS-encrypted RDS database whose password never
appears in code.** It autoscales on CPU and request count, alerts on the golden
signals, and ships with scripts that verify the security controls against the
live account.

It began as a course lab (UMGC CLCS 645) that ran containers on public IPs and
passed the database password as plain text. This repo is the hardened rebuild.
**[See the 14 findings and fixes →](docs/hardening-v1-to-v2.md)**

## Quick start

Prerequisites: AWS CLI v2 with an SSO profile, Terraform >= 1.10, `jq`, and a
domain with a public Route 53 hosted zone (optional; without one the stack runs
in HTTP-only demo mode).

```bash
# 1. One-time account setup: state bucket, GitHub OIDC role, $50 budget
cd bootstrap && terraform init && terraform apply -var="budget_alert_email=you@example.com"

# 2. Configure and deploy (about 20-25 minutes)
cd ../environments/dev
cp backend.hcl.example backend.hcl            # bucket = <state_bucket output>
cp terraform.tfvars.example terraform.tfvars  # domain_name, alert_email
terraform init -backend-config=backend.hcl
terraform apply

# 3. Prove it
cd ../.. && make smoke && make security

# 4. Tear down when finished
make destroy
```

Load testing, failure drills and troubleshooting: [docs/runbook.md](docs/runbook.md)

## Security controls

Every control, how it is implemented and how it is verified, plus the accepted
lab trade-offs: [docs/security-controls.md](docs/security-controls.md).

Highlights:

- Nothing in the app or data tier has a public IP; the database subnets have no route to the internet at all.
- The DB password is generated by RDS, stored in Secrets Manager under a customer-managed KMS key, and injected at runtime.
- There are no AWS access keys anywhere: SSO locally, OIDC in CI, and CI is read-only ([ADR 0005](docs/adr/0005-plan-in-ci-apply-by-hand.md)).
- Every pull request is scanned with checkov; each skipped check is justified in [`.checkov.yaml`](.checkov.yaml).

## Glossary (for non-technical readers)

| Term | Meaning |
|------|---------|
| Terraform / infrastructure as code | Writing the cloud setup as code, so it can be reviewed, versioned and rebuilt identically instead of clicked together by hand |
| Availability Zone | A separate AWS data center within a region; using three means one can fail without an outage |
| Container (ECS Fargate) | A packaged copy of the application that AWS runs without anyone managing servers |
| Load balancer (ALB) | The front door that spreads visitors across the running copies of the site |
| WAF | Web application firewall; filters malicious requests before they reach the site |
| Encryption key (KMS) | The key that scrambles stored data so it is unreadable without permission |
| Private subnet | A part of the network with no direct path from the internet |
| CI (continuous integration) | Automated checks that run on every proposed change |
